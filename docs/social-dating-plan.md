# 社交交友项目改造方案

## 1. 产品定位

- 项目方向：从当前通用管理系统，升级为一个面向年轻用户的社交交友平台。
- 产品目标：同时提供后台管理端、小程序端、安卓 App 端，形成“拉新、匹配、互动、运营、风控”一体化闭环。
- 一期原则：先做可运营、可发布、可扩展的 MVP，不在第一阶段硬上复杂实时音视频或重付费链路。

## 2. 三端定位

### 后台管理端

- 用户审核：资料审核、头像审核、举报审核、黑名单管理。
- 内容运营：轮播位、推荐位、活动话题、公告、标签池管理。
- 匹配运营：推荐策略开关、用户权重、活跃度规则、拉新活动配置。
- 数据看板：注册转化、实名认证、匹配成功率、消息活跃、付费转化。
- 客服风控：举报工单、敏感词命中、设备异常、账号封禁。

### 小程序端

- 主要用途：轻量拉新、快速注册、资料完善、附近推荐、活动报名。
- 核心特点：低门槛进入、强分享传播、适合做增长入口。

### 安卓 App 端

- 主要用途：深度使用、持续互动、聊天陪伴、会员权益承载。
- 核心特点：承载主业务流程，后续适合扩展即时聊天、语音房、动态广场、付费能力。

## 3. 一期 MVP 范围

### 用户侧

- 手机号/账号注册登录
- 个人资料卡
- 头像与相册
- 兴趣标签
- 推荐列表
- 喜欢/跳过
- 双向喜欢提示
- 基础聊天会话占位
- 举报与拉黑

### 运营侧

- 用户总览
- 推荐位配置
- 标签配置
- 审核任务池
- 举报处理台
- 内容与公告配置

### 技术侧

- 统一用户体系
- 社交业务 API
- 后台运营看板
- 小程序/安卓共用接口
- Jenkins 持续发布链保持不变

## 4. 技术落地建议

### 后端

- 继续使用现有 `RuoYi Cloud + Spring Cloud` 体系。
- 第一阶段优先把社交业务能力挂在现有 `ruoyi-system` 中，避免新增独立微服务后又要改部署、网关、Nacos、容器编排。
- 等社交业务稳定后，再考虑拆分为独立 `social` 微服务。

### 前端

- 当前 `zoumh-vue3` 先承担：
  - 对外落地页
  - 后台管理首页/运营驾驶舱
- 小程序端与安卓端建议后续单独建仓：
  - 小程序：`uni-app`
  - 安卓：`uni-app Android` 或原生/Flutter

## 5. 数据模型建议

一期建议优先建立以下核心表：

- `social_user_profile`
- `social_user_media`
- `social_user_tag`
- `social_recommend_log`
- `social_like_record`
- `social_match_record`
- `social_chat_session`
- `social_report_record`
- `social_banner`
- `social_topic`

## 6. 迭代节奏

### 第一阶段：项目换壳与骨架成型

- 首页改为社交交友产品形态
- 后台首页改为社交运营驾驶舱
- 增加社交业务基础接口
- 补充社交项目规划文档与 SQL 草案

### 第二阶段：用户资料与推荐

- 资料编辑
- 标签体系
- 推荐流
- 喜欢/跳过
- 双向匹配

### 第三阶段：互动与运营

- 聊天会话
- 举报审核
- 公告活动
- 用户分层

### 第四阶段：商业化

- 会员体系
- 超级曝光
- 礼物/活动权益
- 数据转化看板

## 8. 后续默认假设

- 品牌名先使用 `Zoumh Social`
- 面向人群先按“城市年轻单身用户”设计
- 小程序作为拉新入口，安卓 App 作为主使用端
- 后台继续复用现有若依权限体系
